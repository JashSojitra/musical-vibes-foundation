# Safe local-content migration

No live writes or asset uploads have been performed. The migration defaults to dry-run; a token alone cannot trigger writing.

## Inventory and identity

`npm run sanity:migrate:dry` validates original local file mappings, duplicate IDs/slugs and references without connecting to Sanity. It generates `.tmp/sanity-migration/manifest.json` with document mappings, source filenames, SHA-256/SHA-1 hashes, bytes, slug preservation, count inventory and expected stable collection IDs. Treat the manifest as an operator artifact; keep it privately with the migration backup/receipt.

Expected import: 6 programs, 3 events, 3 Journal archive notes, 12 media records / 12 unique original photographs, 7 FAQs and one settings singleton (32 content documents). Original photographs come from the preserved gallery manifest, not resized WebP derivatives. Program/event/Journal IDs remain unchanged; media document IDs are `media.<local-id>` and retain the original ID in `sourceId`. FAQs use deterministic ordered IDs. All routes retain their slugs.

The three notes retain publication date **2026-11-03**. Their original **2025 event dates** stay on referenced events. Body text is converted to Portable Text without inventing updates. Derived Gallery collection IDs and relationships remain unchanged after import.

Every imported media record retains `consent: unconfirmed`, starts with `editorialApproval: pending` and `publicationEnabled: false`, and preserves its standalone flag. This intentionally produces an empty photo Gallery until the owner reviews rights and enables/publishes photographs. Review permissions outside Sanity; never upload consent evidence to this public dataset. This is a cutover prerequisite, not a migration failure.

## Explicit operator sequence

1. Keep website builds in `CONTENT_SOURCE=local`. Pause owner editing during import. Create a private dataset export including drafts and assets using the Sanity CLI (`sanity dataset export production <private-backup-path>` from `studio/`) and separately preserve local originals. Verify the export can be read and record the initial dataset counts. Do not keep backups in the repository or public dataset.
2. Run `npm ci`, then `npm run sanity:migrate:dry`. Inspect the manifest, counts, mappings, dates and original hashes. Fix missing files/references before proceeding. Rerunning dry-run is safe.
3. Only when explicitly authorized to migrate, create a temporary least-privilege write token permitted by the Free project (Editor token where available); set server/operator-only `SANITY_API_WRITE_TOKEN` in the shell or ignored env file. The scripts read process environment; use Node's `--env-file=.env.local` with `--import tsx scripts/sanity-migration.ts --write` if loading a file, or set shell variables before the npm command. A write token is not a Studio login and is never configured in the public site.
4. Run `npm run sanity:migrate:write`. This is the sole data-writing command. The target is checked against `6jpdhhxg/production`. Existing recognized published IDs are skipped, never overwritten; unexpected IDs, draft-only occupants of a migration ID, or conflicting slugs abort before uploading. SHA-256 deduplicates original uploads within the run; Content Lake `sha1hash` lookup reuses existing assets across reruns, including after interruptions. Missing documents are created in one transaction with stable strong references; concurrent ID creation aborts rather than overwriting or claiming someone else's document in the receipt. Do not run multiple migration operators concurrently.
5. Retain `.tmp/sanity-migration/receipt.json` (new document and uploaded asset IDs) and the manifest. A failure prints its cause and returns a nonzero exit code. If upload fails, documents are not committed; uploaded assets may remain and are reused on rerun. If a process stops between a successful transaction and receipt persistence, reconcile actual IDs against the manifest and pre-import backup before rollback. Never infer that an incomplete receipt authorizes deleting an existing asset.
6. Run `npm run sanity:migrate:verify`. It performs read-only count comparison for all mapped IDs, slug and image-reference checks and adapter mapping. It writes `.tmp/sanity-migration/verification.json`. Review owner changes if a slug differs rather than rerunning an overwrite. Confirm image assets and relationship previews in Studio. This comparison scopes counts to imported IDs so unrelated pre-existing content is not mistaken for an import duplicate.
7. Owner checks permissions and alt/captions, changes eligible photographs to approved + public, and publishes those changes. Review crop/hotspot on phone and desktop. Verify all 3 derived collections and standalone archive against the manifest once approved. Journal text remains published even when photographs are withheld.
8. Complete the actual Workers CMS publishing/rename/unpublish/withdrawal acceptance cycle in [integration instructions](SANITY-INTEGRATION.md). Only then separately authorize deployment/cutover. Revoke the write token and privately archive the evidence.

## Rollback and recovery

The fastest site rollback is a separately approved rebuild/deployment with `CONTENT_SOURCE=local`, using the unchanged repository data; no data deletion is needed. Merely setting a runtime variable cannot restore prerendered content from a different build mode.

For a mistaken dataset import, pause editing, take another private export and compare the original backup, manifest, receipt and actual dataset. Identify **only** documents newly created by this run and confirm no subsequent owner edits or external references depend on them. Delete Journal and settings/FAQ references before programs/events/media (or all reviewed new documents in one explicit transaction). Never delete all documents by type or by broad prefix. Restore edited pre-existing documents from the backup if separately needed; this script never overwrites them. Asset cleanup is optional: delete only receipt-listed newly uploaded assets with no references anywhere, including drafts. Preserve any asset that existed before the run or is now reused. Revoke the temporary token afterward.

Sanity validation is editorial guidance; direct API operators can bypass it. Keep import review and backups as operational requirements. A dataset restore must preserve IDs and slug history. Test backup restore in a separate allowed public dataset only with separate authorization; never replace production just to test.
