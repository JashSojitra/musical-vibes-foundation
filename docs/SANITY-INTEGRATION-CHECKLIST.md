# Sanity integration checklist

Implementation is available in the separate Studio and typed CMS adapter. See [SANITY-INTEGRATION.md](SANITY-INTEGRATION.md) and [validation status](SANITY-VALIDATION.md). The checklist below is the original preparation contract; uncached request-time reads replace its proposed webhook/cache layer. Live migration, permission review and production cutover remain explicit manual steps.

Preparation only: no project, dataset, Studio, credentials, dependencies or webhook endpoint has been created. This plan extends the existing [content architecture](CONTENT-ARCHITECTURE.md), `src/types/content.ts` and `src/lib/journal.ts`.

## Schema contract

Use root-safe Sanity storage IDs with no periods; preserve stable local IDs in `sourceId` through an explicit map. Dotted document IDs are private paths even in a public dataset. Preserve public collection IDs `journal-collection.<local-journal-id>` even when Sanity IDs differ. Do not use titles or slugs as relationship keys. Existing dotted-ID data needs separately authorized repair; see [public access diagnosis](PROGRAMS-PUBLIC-ACCESS.md).

| Schema                   | Required fields and mapping                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `journalEntry`           | `title`, unique `slug`, `previousSlugs[]`, `excerpt`, `body` (Portable Text from `paragraphs`), `kind` (`event/update/news`), `publishedAt`, optional `event` reference, `programs[]` references, ordered `photos[]` references to `mediaItem`. Preserve local ID in `sourceId` when needed. Require an event reference for event stories that should produce collections.          |
| `event`                  | Existing ID, `title`, unique `slug`, `previousSlugs[]`, `date` (date-only to preserve archive semantics), `dateLabel`, `status` (`past/upcoming`), optional `location`, `description`, `image` media reference, ordered `gallery` media references, `sourceAlbum`. Future timed events may add timezone-aware `startsAt/endsAt`; do not silently convert existing date-only events. |
| `program`                | Existing ID, `slug`, `previousSlugs[]`, `number`, `title`, `category`, `headline`, `description`, `body` from paragraphs, `focus[]`, `image` media reference, `imageContext`, `theme` constrained to current theme values.                                                                                                                                                          |
| `mediaItem`              | Stable ID, Sanity `image` with crop/hotspot, required `alt`, `caption`, category enum from `MediaAsset`, `source`, original focal `position`, `editorialApproval` (`pending/approved/rejected`), `publicationEnabled`, `standaloneGallery` default **false**. Preserve `consent: unconfirmed` from the import. Dimensions come from the image asset metadata.                       |
| `siteSettings` singleton | Current name, URL, email, phone, location and mission; `featuredPrograms[]` / `featuredEvents[]` references replacing homepage slug selections.                                                                                                                                                                                                                                     |
| `faq`                    | Stable migration ID, question, answer, current category enum and explicit sort order.                                                                                                                                                                                                                                                                                               |

Private rights evidence/reviewer details should live in a protected dataset or document permission boundary if the editorial dataset is public. Merely hiding a Studio field does not make it private. Owner verification of the existing unconfirmed media rights remains a launch prerequisite; editorial approval is a separate field.

**No `galleryCollection` document.** Fetch published Journal entries plus eligible media, then reuse the current adapter projection for Gallery, homepage previews and Events teasers. The standalone archive remains an explicit `standaloneGallery` flag on the same media records. Upload each original once. Deduplicate public photo unions by stable media ID. News/update entries and empty event entries do not generate collections.

Sanity's published perspective excludes drafts and versions. Map published documents into the adapter's `status: published`, exclude future publication dates, and keep drafts in an authenticated preview path. Unpublishing removes the public document; do not expose draft IDs or treat any fetched draft as published. [Official client reference](https://github.com/sanity-io/client#using-perspectives).

## Future environment contract

These names are planned; the current app does not read them. Select actual values only when the owner configures a project.

| Variable                                            | Scope / purpose                                                                                                                                |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_SANITY_PROJECT_ID`                     | Public project identifier.                                                                                                                     |
| `NEXT_PUBLIC_SANITY_DATASET`                        | Public dataset name; decide staging and production separation.                                                                                 |
| `NEXT_PUBLIC_SANITY_API_VERSION`                    | Fixed, reviewed API date string; never compute from today's date.                                                                              |
| `SANITY_API_READ_TOKEN`                             | Server-only, least privilege; required for private dataset reads or authenticated previews, not normally public published reads.               |
| `SANITY_REVALIDATE_SECRET`                          | Server-only signing secret for validated publication/media-change webhook requests.                                                            |
| `SANITY_PREVIEW_SECRET`                             | Optional custom server-only preview admission secret if that approach is selected; use the official authenticated preview flow where possible. |
| `SANITY_API_WRITE_TOKEN`                            | Migration operator environment only; never browser or ordinary website runtime. Revoke after import.                                           |
| `SANITY_STUDIO_PROJECT_ID`, `SANITY_STUDIO_DATASET` | Proposed explicit Studio config inputs if a separate Studio is chosen; public identifiers, never tokens.                                       |

Use ignored `.env.local` locally and the eventual host's secret store in production. Only identifiers/API version may have a public prefix. Confirm the exact SDK/preview integration against the selected Next.js or vinext release before installation. [Sanity Next.js client configuration](https://www.sanity.io/docs/nextjs/configure-sanity-client-nextjs), [authenticated preview guidance](https://www.sanity.io/docs/visual-editing/implementing-draft-mode).

## Integration sequence and acceptance

1. Choose the project owner, dataset visibility, editor roles and staging environment. Decide separate Studio versus embedded Studio after Workers compatibility testing. Allow only the actual development/preview/production origins in CORS; enable credentials only for authenticated editor origins.
2. Export the local content and stable ID/slug/reference manifest. Record source asset hashes, originals, dimensions and focal positions. Dry-run schema validation and duplicate/missing-reference checks before writing.
3. Import program/event identities, upload media once, create `mediaItem` records, then resolve image/gallery references and import Journal entries, settings and FAQs. Preserve the three archive notes' **2026-11-03 publication date** separately from their actual **2025 gathering dates**. Keep all existing route slugs. Preserve the standalone archive flags explicitly.
4. Replace the adapter's local read boundary with server-side Sanity queries, retaining the projection and visibility rules. Retire the event-derived `journalSeed` source when imported entries become authoritative, so archive notes are not generated twice. Keep an explicit local fallback only if its freshness/publication policy is defined.
5. Render Portable Text with the existing editorial styling; preserve metadata, canonicals, JSON-LD, sitemap and 404 behavior. Add redirects from `previousSlugs`, and invalidate both old and new paths when a slug changes.
6. Query only the `published` perspective for public output. Require `publicationEnabled && editorialApproval == approved` for every public media usage, including old program/page imagery. Keep preview uncached and authenticated. Never let Journal-only draft photographs leak into the standalone archive.
7. Add a signed webhook handler for create/update/delete/publication/unpublication and media approval changes. Invalidate affected articles, `/journal`, `/gallery`, `/events`, homepage previews and sitemap, including deleted references and old slugs. Use idempotence and bounded TTL recovery; verify withdrawal actually removes cached output. Sanity documents signature validation and tag invalidation in its [webhook guide](https://www.sanity.io/docs/nextjs/validating-sanity-webhooks-nextjs). Test the chosen APIs on the eventual Workers runtime before relying on them.
8. Deliver responsive images from Sanity CDN with bounded widths, dimensions and crop/hotspot. Choose the appropriate `next/image` loader/remote patterns or vinext image adapter after hosting selection; avoid duplicate full-resolution downloads. Keep social preview images deterministic.
9. Re-run the current publication/approval model tests and browser journeys against staging: publish/edit/rename/unpublish/re-publish; revoke media approval; future dates; missing references; zero-photo entries; duplicate references; standalone-only content; Journal → Gallery → Journal links; mobile, SEO and cache withdrawal. Compare imported counts and stable collection IDs with the export manifest.
10. Review owner media permissions, prepare dataset export/restore and rollback instructions, then approve production content integration separately. No credentials or Sanity setup are part of this navigation commit.
